# 语音响应与第二幕衔接优化

本记录最初对应 2026-10-16 的本地优化；同日已按后续要求部署到 `pi@10.87.80.207`，详见[部署复测记录](部署记录-2026-10-16.md)。GitHub 暂未推送。
现场反馈来自树莓派原来的后台版本，该版本尚无本地新增的蜜蜂提示音。

## 定位依据与边界

1. `get_asr()` 原来在首句 `transcribe_wav()` 时才初始化识别器；首句“执行机体自检”的处理路径包含模型加载和首次推理。未取得本次现场日志，不能量化它实际占了多少秒，也不能断言它是现场延迟的唯一原因。
2. 本地新增的 0.6 秒结束提示原来在识别之前串行播放，部署后会增加这段等待，因此同时调整两者的调度。
3. 第二幕原有固定等待为 5、8、8 秒，总计 21 秒。
4. 用 FFmpeg 检查本地环境音效：`se-3`、`se-4` 内部分别约有 2.10、3.84 秒静音，三段均另有约 0.4 秒尾部静音。检测阈值为 -45 dB，范围为至少 0.25 秒的静音。
5. 检查 `act1` 开头 8 秒未检出超过 0.15 秒的静音；串口打开路径中也没有显式固定延时。本次没有修改第一幕音频或串口协议。

## 本地修改

语音模式启动时执行 `prepare_listening()`，加载模型并用 0.5 秒静音完成一次推理。
模型准备成功后才进入唤醒等待；同一进程后续台词复用，准备失败时不进入唤醒。

连续台词完成录音、关闭麦克风并保存文件后，由一个工作线程执行识别，主线程同时播放结束提示。
两者均完成后才返回文字给状态机。识别失败、提示音失败和退出路径均等待工作线程收尾，避免把任务留给下一句。
直接调用 `record_utterance()` 默认仍播放完整的前后提示；只有连续识别入口接管结束提示，避免重复播放。

剧本句尾停顿改为 0.4 秒，VAD 阈值、最短语音长度、最长录音和台词匹配规则沿用原值。
如连贯台词中的停顿导致误断句，可把 `listening.silence_seconds` 调回 0.55。

第二幕固定等待改为 2、2、2 秒，共减少 15 秒。
三段环境音效仅删除已检测的长静音，内部保留约 0.12 秒、结尾保留约 0.1 秒的余量；有效音效内容不裁剪。

| 音效 | 原时长 | 新时长 |
|---|---:|---:|
| se-3 | 8.41 秒 | 6.16 秒 |
| se-4 | 10.14 秒 | 6.16 秒 |
| se-5 | 6.69 秒 | 6.16 秒 |

三段音效合计缩短约 6.74 秒，连同固定等待共约 21.74 秒。
此数值依据配置和素材计算，不是树莓派现场测量的整段耗时，且不包含播放器启动开销。

## 本地验证

73 项回归检查、剧本配置检查及完整五幕纯模拟通过。
新增用例先确认旧程序未预热、结束提示串行和第二幕等待过长，再验证新顺序和异常收尾；并行测试使用事件互相确认，不用模拟耗时推算实机提速。
三个重编码音效正常解码，未检测到至少 0.25 秒的静音；时长和大小索引与实际文件一致。
第一幕音乐和另外提交更新的蜜蜂提示音均保持原有字节内容。

并行实现使用单个识别工作线程。上游当前的 [Python 绑定](https://github.com/k2-fsa/sherpa-onnx/blob/master/sherpa-onnx/python/csrc/offline-recognizer.cc#L150-L151)在解码时释放 GIL，支持 Python 主线程继续调度提示音；树莓派所装版本及其实际性能尚未复测。

## 后续复测

日志会显示模型准备耗时，以及每句“转文字”和“含结束提示”的耗时。
部署后先使用 `--silent-actions` 测试首句与后续句子的响应、长句断句和第二幕衔接，再进行实体动作排练。
本地开发环境没有安装真实 sherpa-onnx 运行库，本地阶段未测量真实识别速度。同日部署后，树莓派 73 项回归、真实 Silero 分句和提示/识别并行检查通过；离线样例预热后转文字约 0.18～0.26 秒，包含结束提示的处理约 1.11 秒。真人现场响应及动作效果仍需排练确认。
