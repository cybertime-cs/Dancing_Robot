# 串口排查与修复 · 2026-10-06

## 实际端口

当前树莓派 `pi@10.189.47.207` 使用 `PI_SERIAL_PORT=/dev/serial0`，
实际映射为 `/dev/ttyAMA10`，对应树莓派单独的调试 UART 接口。
波特率为 115200，8 数据位、无校验、1 停止位（8N1），关闭软硬件流控。
串口登录服务未占用该端口。动作已执行说明指令发送链路曾经成功，不能据此确认返回链路始终正常。

## 已确认的软件问题

1. 原接收代码要求一次读取的全部字节恰好等于一个回执。
   分段回执、多个回执粘连、回执前后出现其他数据都会漏判；读后清空缓冲区还可能丢失后续字节。
2. 原超时使用系统时间。实际日志标称等待 180 秒，但根据日志的单调时间戳，
   只经过 11.817961 秒就超时；同期系统时间跳变 84315.492548 秒，导致提前中止。

没有开启原始收发记录时，单凭“串口超时”不能证明下位机没有发送回执。

## 修复行为

- 超时与耗时改用单调计时，不受系统校时影响。
- 连续累积接收字节，识别已知完整回执，兼容分段与粘连。
- 只在发送前清理遗留数据，发送后不清空接收缓冲区。
- 使用非阻塞读取、写入超时和串口独占请求。
- 超时日志区分“未收到任何数据”和“收到数据但未识别约定回执”。
- 原始收发与识别结果写入 `deployment_logs/serial-trace.jsonl`。
- 仍使用原有两种回执定义，没有增加猜测的回执类型，不自动重发动作。

当前沿用的回执字节：

```text
ff 00 05 05 00 00 18 22
ff 00 05 05 00 00 19 22
```

这些帧不包含本次命令序号，清理发送前遗留数据可减少误判，
但迟到的上次回执仍无法严格归属到具体动作。不同状态的物理含义需核对下位机协议。

## 现场复测

正常查看服务日志：

```bash
journalctl _SYSTEMD_USER_UNIT=fenghou.service -f -o cat
```

查看原始记录：

```bash
cd /home/pi/queen_robot
tail -n 30 deployment_logs/serial-trace.jsonl
```

记录中的 `TX` 为发送，`RX` 为实际读取，`ACK` 为识别成功；
`TIMEOUT` 的 `received_bytes` 显示本次累计收到的字节数量。
`elapsed_seconds` 使用单调计时，时间日期即使被校正也不影响该耗时。

若动作已执行但 `received_bytes=0`，下一步检查下位机是否实际发送、下位机 TX 到树莓派 RX 的连接、共地与接触情况。
若收到其他字节，需要根据原始十六进制数据与真实下位机协议核对，而不是盲目延长等待时间。

软件和虚拟串口检查不会驱动机器人，真实回执效果仍需现场触发动作后确认。

本次验证：修复前回归复现了分段、粘连、旧回执和系统时间跳变问题；
修复后本地和树莓派的 61 项测试通过。树莓派虚拟串口验证了分段、粘连和非约定数据的处理，
服务已恢复到唤醒等待。
